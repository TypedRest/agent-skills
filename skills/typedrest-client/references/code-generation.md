# Code generation from OpenAPI

The generator reads an OpenAPI/Swagger document, infers TypedRest endpoints from patterns in its paths and emits a client. It comes in two forms that share the same inference:

- **Source generator** (`TypedRest.SourceGenerator`, C# only): generates during compilation; nothing is written to the source tree; a changed spec takes effect on the next build. Interfaces and DTOs are generated by default.
- **CLI** (`typedrest-codegen`, all languages): writes source files to disk. Interfaces and DTOs are opt-in. Must be rerun when the spec changes.

The CLI needs the .NET SDK (version 10 or later) even when generating Java, Kotlin or TypeScript. If `dotnet --version` fails or reports an older version, tell the user the SDK is required (https://dotnet.microsoft.com/download) rather than working around it.

## 1. Install the CLI

Install it even for C# source generator projects: step 2 uses it.

For a repository, prefer a local tool manifest so that the version is pinned and CI can restore it:

```bash
dotnet new tool-manifest   # only if .config/dotnet-tools.json does not exist yet
dotnet tool install typedrest-codegen
```

Run it as `dotnet typedrest-codegen ...` (after `dotnet tool restore` on a fresh checkout). For a one-off, `dotnet tool install -g typedrest-codegen` and plain `typedrest-codegen ...` work too. The commands below use the plain form.

## 2. Inspect the inference

Paths are arranged into a tree, with placeholders such as `/contacts/{id}` collapsed into a wildcard node. Each node is matched against these patterns; the first match wins:

| Pattern    | Matches a path with                                                                 | Endpoint   |
| ---------- | ----------------------------------------------------------------------------------- | ---------- |
| Collection | `GET` returning an array of `T`, and a child wildcard path with `GET` returning `T` | Collection |
| Indexer    | a child wildcard path, but no matching array response                               | Indexer    |
| Element    | `GET` with a JSON response body                                                     | Element    |
| Function   | `POST` with both a JSON request and a JSON response body                            | Function   |
| Consumer   | `POST` with a JSON request body                                                     | Consumer   |
| Producer   | `POST` with a JSON response body                                                    | Producer   |
| Action     | `POST` with neither                                                                 | Action     |
| Blob       | `GET` with a non-JSON response body                                                 | Blob       |
| Upload     | `POST` with a non-JSON request body                                                 | Upload     |
| Default    | none of the above, but child paths that matched                                     | plain endpoint holding the children |

Write the inferred structure into the spec as an `x-typedrest` extension:

```bash
typedrest-codegen pattern -f myapi.yml
```

Before running it:

- **Commit the spec first** (or at least make sure it is unmodified in Git). `pattern` rewrites the whole file in normalized form, so the diff is noisy.
- **Run it only once.** It always re-runs the inference and replaces an existing `x-typedrest`, discarding hand edits. If the spec already contains `x-typedrest`, do not run `pattern` on it; edit the extension by hand, or write to another file with `-o` and compare.
- If the user does not want the spec modified (for example it is a vendored upstream file), write to a copy with `-o myapi-annotated.yml` and generate from that, or skip annotation entirely and rely on the inference as long as it is correct.

Then read the extension and compare it with the API. Report to the user what was inferred and what looks wrong. Common misses:

- An endpoint returning `text/event-stream` or a long-lived stream was inferred as `blob`.
- A resource that should be polled was inferred as a plain `element`.
- A list path without a `{id}` child, or whose array item type differs from the element type, was not inferred as a collection.
- Operations using verbs or parameters that no pattern looks at (query parameters, `PUT`-only resources, `DELETE` with a body) are missing. These become custom code later.
- Paths with only unmatched operations are dropped entirely.

## 3. Fix the inference with x-typedrest

When a document contains `x-typedrest`, both the source generator and `generate` use it as-is instead of inferring. Edit it by hand. It is a tree of endpoints keyed by the property names to generate:

```yaml
x-typedrest:
  contacts:
    kind: collection
    uri: ./contacts
    description: Collection of contacts.
    schema:
      $ref: '#/components/schemas/Contact'
    element:
      kind: element
      description: A specific contact.
      children:
        note:
          kind: element
          uri: ./note
          schema:
            $ref: '#/components/schemas/Note'
        poke:
          kind: action
          uri: ./poke
        events:
          kind: sse
          uri: ./events
          schema:
            $ref: '#/components/schemas/ContactEvent'
```

Every endpoint takes `kind`, `uri`, `description` and `children`. Additional properties per kind:

| `kind`                 | Additional properties               |
| ---------------------- | ----------------------------------- |
| *(omitted)*            | plain endpoint that only holds children |
| `element`              | `schema`                            |
| `collection`           | `schema`, `element`                 |
| `indexer`              | `element`                           |
| `action`               |                                     |
| `consumer`             | `schema`                            |
| `producer`             | `schema`                            |
| `function`             | `request-schema`, `response-schema` |
| `blob`                 |                                     |
| `upload`               | `form-field`                        |
| `polling`              | `schema`                            |
| `streaming`            | `schema`                            |
| `sse`                  | `schema`, `event-type`              |
| `streaming-collection` | `schema`, `element`                 |

The reactive kinds (`polling`, `streaming`, `sse`, `streaming-collection`) are never inferred; annotating is the only way to get them.

Consequence to tell the user about: once `x-typedrest` exists, **paths added to the spec later are not picked up automatically**. They must be added to the extension by hand, or the extension removed, `pattern` rerun and the edits reapplied.

Descriptions end up as documentation comments in the generated code, so it is worth fixing poor ones.

## 4a. C# source generator (preferred for C#)

```bash
dotnet add package TypedRest.SourceGenerator
dotnet add package TypedRest
```

Add as needed:

- `TypedRest.Reactive` if `x-typedrest` contains any polling or streaming kinds.
- `TypedRest.SystemTextJson` if the serializer is set to `system-text-json`.

Reference the spec in the project file:

```xml
<ItemGroup>
  <TypedRestOpenApi Include="myapi.yml" ServiceName="MyService" Namespace="MyCompany.MyService" />
</ItemGroup>
```

`ServiceName` is required and names the entry endpoint (`MyServiceClient`). `Namespace` defaults to `$(RootNamespace)`. Interfaces, DTOs and the entry constructor are generated by default; the serializer defaults to `newtonsoft`. The other metadata (`DtoNamespace`, `GenerateInterfaces`, `GenerateDtos`, `GenerateEntryConstructor`, `Serializer`), the matching project-wide MSBuild properties (`TypedRest` prefix, e.g. `<TypedRestSerializer>`) and the `TRCG*` diagnostics are listed in the configuration reference: https://github.com/TypedRest/CodeGeneration/blob/master/src/TypedRest.SourceGenerator/README.md

Notes:

- Several specs in one project: one `TypedRestOpenApi` item each, with distinct `ServiceName` and `Namespace`, otherwise the generated types collide.
- To read the generated code, set `<EmitCompilerGeneratedFiles>true</EmitCompilerGeneratedFiles>`; the files then also appear under `obj/`. Do this while developing custom code so you can see the exact generated names and signatures. Do not check those files in.
- Only local `$ref`s are resolved. Bundle a multi-file spec into a single document first.
- In a library that is packed as a NuGet package, the source generator is a build-time dependency only. Mark its `PackageReference` with `PrivateAssets="all"` so that consumers of the library do not get the generator themselves.
- The generator runs inside the compiler and therefore depends on the Roslyn version of the installed .NET SDK. If the build warns that the generator could not be loaded, or no client types appear, check the current requirement under "Limitations" at https://typedrest.net/code-generation/source-generator/ and either update the SDK or fall back to the CLI.

## 4b. CLI (Java, Kotlin, TypeScript; C# fallback)

`--file`/`-f`, `--output`/`-o` and `--service-name`/`-s` are required. Always pass `--generate-dtos` unless the project already has the DTO types: generated endpoints reference them by name.

Generate into a location that holds **only generated code** (its own directory, package or namespace), so that it can be deleted and regenerated wholesale and custom code never sits next to it.

### Kotlin

```bash
typedrest-codegen generate -l kotlin -f myapi.yml -o src/main/kotlin/ -s MyService -n com.mycompany.myservice --generate-dtos
```

- `--output` is the source root; files land in a directory tree matching the package. DTOs go to a `dtos` subpackage unless `--dto-namespace` says otherwise.
- Dependencies: `net.typedrest:typedrest`; `net.typedrest:typedrest-reactive` for polling/streaming kinds.
- Serializers: `kotlinx` (default), `jackson`, `moshi`. For `kotlinx` the project needs **both** the `kotlin("plugin.serialization")` Gradle plugin and an explicit `org.jetbrains.kotlinx:kotlinx-serialization-json` dependency; TypedRest only has it as `implementation`, so without it the generated `@Serializable` annotations do not resolve. For `jackson`/`moshi` add `net.typedrest:typedrest-serializers-jackson` / `-moshi`.

### Java

```bash
typedrest-codegen generate -l java -f myapi.yml -o src/main/java/ -s MyService -n com.mycompany.myservice --generate-dtos
```

- Same layout as Kotlin.
- Dependencies: `net.typedrest:typedrest`, `net.typedrest:typedrest-serializers-jackson`, `org.jspecify:jspecify` (optional properties carry `@Nullable`); `net.typedrest:typedrest-reactive` for polling/streaming kinds.
- Serializers: `jackson` (default) or `moshi`. `kotlinx` is rejected for Java.

### TypeScript

```bash
typedrest-codegen generate -l typescript -f myapi.yml -o src/myclient/ -s MyService --generate-dtos
```

- One module per type plus an `index.ts` re-exporting everything. `--namespace` and `--dto-namespace` are directories relative to `--output` (defaults: the output directory itself and `dtos`).
- Dependency: `npm install typedrest`. Reactive endpoints are part of the main package (version 0.5.0 or later).
- `--serializer` and `--generate-interfaces` have no effect.

### C# (fallback)

```bash
typedrest-codegen generate -f myapi.yml -o MyService/ -s MyService -n MyCompany.MyService --generate-interfaces --generate-dtos
```

- Pass `--generate-interfaces --generate-dtos` to match what the source generator does by default.
- `--serializer system-text-json` needs the `TypedRest.SystemTextJson` package. `--lang-version` sets the minimum C# version of the emitted code (same values as MSBuild `LangVersion`).

### Options that matter for custom code

- `--generate-interfaces` (C#, Kotlin, Java): on the JVM it also changes names. The interface takes the plain name (`ContactElementEndpoint`) and the class gets the `Impl` suffix. Without it, the class keeps the plain name. Decide this before writing custom code against the generated names. Use it when consumers should be able to mock the client.
- `--generate-entry-constructor false` (not TypeScript): leaves the entry endpoint's constructor for you to write, which is needed for a custom error handler or default headers. See [extending-generated-code.md](extending-generated-code.md).

Full option reference: https://github.com/TypedRest/CodeGeneration/blob/master/src/TypedRest.CodeGeneration.Cli/README.md, or `typedrest-codegen help generate`.

## 5. Build and show usage

Build the project (`dotnet build`, `./gradlew build` or `mvn compile`, `npx tsc --noEmit`). Fix dependency and configuration problems until it compiles; do not start on custom code before that.

Then show the user what they got. Naming rules, to predict and explain the generated names:

- Entry endpoint: `<ServiceName>Client`.
- `/contacts` becomes a `ContactCollectionEndpoint` exposed as `Contacts` / `contacts`; its element type is `ContactElementEndpoint`.
- Path segments in `kebab-case`, `snake_case` or `camelCase` become `PascalCase` in C# and `camelCase` elsewhere.
- DTOs are named after the schemas in `components`.
- Name clashes are resolved by prefixing the parent's name.

Write the usage snippet in the project's language against the names actually generated. What the generated endpoints and DTOs look like per language, with usage examples: https://typedrest.net/tutorials/from-openapi/

## 6. Keep client and spec in sync

- **Source generator**: nothing to do; every build regenerates.
- **CLI**: make regeneration a single command that lives in the repository, and make drift visible.

Put the exact `generate` invocation in the project's own build tooling rather than in documentation:

- **Gradle**: an `Exec` task (e.g. `generateClient`) that runs `dotnet typedrest-codegen generate ...`. If the generated code is not checked in, make `compileKotlin`/`compileJava` depend on it and add the output directory to the source set; if it is checked in, keep the task manual.
- **Maven**: `exec-maven-plugin` bound to `generate-sources`, or a script next to the POM.
- **npm**: a `"generate"` script in `package.json`; call it from `"prebuild"` if the generated code is not checked in.
- **C# with the CLI**: a script, or an MSBuild `Exec` target that runs before `CoreCompile`.

Ask the user whether generated code should be checked in, if the project does not already show a convention. Checked in means reviewable diffs and no .NET SDK needed to build; not checked in means no drift is possible but every build machine needs the SDK.

If it is checked in, offer a CI drift check: restore the tool, regenerate, then fail when the tree changed.

```bash
dotnet tool restore
dotnet typedrest-codegen generate -l kotlin -f myapi.yml -o src/main/kotlin/ -s MyService -n com.mycompany.myservice --generate-dtos
git diff --exit-code
```

When regenerating, delete the generated directory/package first so that endpoints removed from the spec do not leave stale files behind. This is why custom code must live elsewhere.

Remind the user of the `x-typedrest` rule from step 3 wherever the regeneration command is documented.

## Troubleshooting

| Symptom                                               | Likely cause                                                                                      |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| DTO types not found                                   | CLI run without `--generate-dtos`, or source generator with `GenerateDtos="false"`.               |
| `@Serializable` unresolved (Kotlin)                   | Missing serialization Gradle plugin or explicit `kotlinx-serialization-json` dependency.          |
| `@Nullable` unresolved (Java)                         | Missing `org.jspecify:jspecify`.                                                                  |
| Reactive endpoint types not found                     | Missing `TypedRest.Reactive` / `typedrest-reactive`.                                              |
| Properties arrive empty or under the wrong JSON names | Serializer mismatch between DTO annotations and the entry endpoint.                               |
| New path in the spec does not show up in the client   | The spec has `x-typedrest`; add the path there.                                                   |
| A path is missing although there is no `x-typedrest`  | No pattern matched its operations. Annotate it, or add it as custom code.                         |
| Duplicate type errors with several specs (C#)         | `TypedRestOpenApi` items share a `Namespace` or `ServiceName`.                                    |
| No client types in a C# build                         | Spec not included as `TypedRestOpenApi`, a `TRCG` diagnostic in the build output, or SDK too old. |
| Unresolved `$ref`                                     | Multi-file spec; bundle it into one document.                                                     |
